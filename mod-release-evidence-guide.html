Free guide for independent mod authors

Make compatibility claims you can show your work for

A useful release record answers three questions: exactly what did you test, what happened, and what remains unknown? Keeping those answers together helps you write clearer release notes and makes it easier to repeat a test after a game update.

1. Identify the exact setup

Write down the game build or branch, platform, mod version, required dependencies, relevant load order, and test date. If a setting or save affects the result, note that too. “Tested on the latest version” gets stale quickly; an exact build number gives another person a concrete starting point.

2. Separate package checks from runtime tests

Opening the archive, checking file paths, and confirming expected metadata are package checks. Loading the game and exercising the mod are runtime tests. Record them separately so a clean package review does not get mistaken for proof that the mod works in play.

3. Make each test repeatable

For every test, state the starting conditions, the action you took, what you expected, and what you observed. Include the result even when it fails. A short reproducible issue report is more useful than “seems broken” because it gives you or another author a way to try the same steps.

Example: With build [number] and mod version [number], start a new test save, enable [feature], then perform [action]. Expected: [result]. Observed: [result]. Result: [pass/fail/not run].

4. Keep evidence connected to the test

Give screenshots, logs, or recordings a filename that points back to the test session. Note what each item demonstrates and what it cannot demonstrate. Before sharing, remove private paths, account names, or other personal details that are not needed to understand the result.

5. Say what you did not test

State known limits plainly: other game branches, multiplayer, unusual load orders, or long sessions may not have been covered. A narrow claim backed by clear evidence is more useful than a broad promise that the test did not establish.

“Tested on build [number] in [environment] on [date]: [specific actions] passed. Multiplayer and earlier branches were not tested.”

Turn the record into release notes

Summarize the tested build, the important checks, known issues, and the limits of the test. Keep the source record so you can update the claim when the game or mod changes. Do not present a static package check as a gameplay result, and do not claim compatibility for versions you did not test.
